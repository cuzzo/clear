## 1. ✅ FIXED: `transpile-tests/74_shared_promise` (BC, double-free)

`Promise(T).next()` (`zig/lib/data-structures.zig:505`) destroys the
Inner after wait. BC's `AWAIT` op called `next()` on every consumption,
so `NEXT sp; NEXT sp;` on a `~T@shared` double-freed Inner.

**Fix:** BC's `exec!()` now caches resolved Promise values in a
`futureResolved: HashMap<Value>` keyed by `futureTable` index. Second
AWAIT short-circuits the cache. Same shape applies to the await-all
list path (`NEXT futures: ~T[]@list`).

**Verification:** Zig unit test in
`zig/lib/data-structures-test.zig` pins the Promise contract;
303/303 BC supportable tests passing (was 302/303).

## 2. ❎ NOT REPRODUCIBLE: `concurrent/02_concurrent_search`

The 3 cited bugs (BG-in-MethodCall escape promote, `.rodata` literal
free, frame-arena UAF from loop rewind) were resolved by infrastructure
changes since the tracker was written:

- `AST.each_bg_block_in_stmt` (`src/ast/ast.rb:111-125`) now descends
  into `MethodCall` and `FuncCall` args, catching `tasks.append(BG{...})`.
- `result.string_captures << name if t&.string?` is still in
  `capabilities.rb:501` but **has no consumers** — the downstream
  `defer alloc.free()` was removed.
- `BgBlock.capture_string_dupes` (`mir_pass.rb:544-546` →
  `mir_lowering.rb:3357-3368`) heap-dupes captured strings AT THE
  SPAWN SITE (before the loop frame restore). Loop rewind no longer a
  UAF source.

**Verification:** 18+ runs across default / `--optimized` / `--safe`
build modes at `THREADS=2/8/$(nproc)`, all clean.

## 3. ❎ NOT REPRODUCIBLE: `concurrent/03_atomic_contention`

`spawnPinned`'s round-robin distribution is still in
`runtime-header.zig:3379-3398`, but BG blocks that capture `@local`
resources now lower to `rt.getSched().submitSpawn(...)` (current
scheduler) instead of `CheatHeader.spawnPinned(...)`
(`mir_lowering.rb:3349`). The compiler emits the user-visible note
`"BG block auto-pinned — captures @local resource (same-scheduler
affinity)"` for the auto-pin case. All 1024 fibers inherit the spawn
site's scheduler; the `*Counter` cache line stays in one core's L1.

**Verification:** 25+ runs at `THREADS=2/4/8/16/32`, Counter
consistently `10240000` (no torn writes, no crashes).

## 5. 🟧 PARTIAL: `concurrent/14_nested_lock` LockCycle false positive

**Investigation reproduced the failure** at `CLEAR_THREADS>=4` with
the bench's strict address-sorted multi-resource WITH workload (which
should be cycle-free). Root cause traced to a TOCTOU on the cycle
detector's chain walk:

- `Task.waiting_for_lock_owner` was a plain `?*Task` field (not
  atomic). Concurrent unlock + reader on different cores observed
  inconsistent (lock, owner) snapshots.

**Partial fix shipped:**

- `Task.waiting_for_lock_owner` is now `std.atomic.Value(?*Task)`
  (`queues.zig:390`).
- Park/unlock writers now order their stores so a reader pairing an
  `.acquire` load on `waiting_for_lock` with the holder's most recent
  `.release` store sees a consistent per-Task snapshot:
  - Park: owner store (`.release`) BEFORE lock store (`.release`).
  - Unlock-wake: lock store (`.release`) BEFORE owner store (`.release`).
- `detectCycle` reads `waiting_for_lock` first; if null, breaks out
  (holder isn't actually parked, the chain link is invalid regardless
  of what `waiting_for_lock_owner` still says).
- Default debug-mode `lock_timeout_ms` bumped from 100ms to 5000ms
  (`scheduler.zig:237`) so high-contention workloads have realistic
  room without strangling on aggressive timeouts.

**What still doesn't work:** The N-Task chain walk is fundamentally
not a single atomic snapshot. Even with per-Task fields atomic and
ordered, the BENCH at `THREADS>=4` still reports `LockCycle` panics
(re-walks consistently observe the same chain even though the
underlying state must be inconsistent — diagnostic dumps show
`waiting_for_lock=null` immediately after the panic fires). The
chain dump shows what looks structurally like an AB/BA cycle, but
the bench's address-sorted `WITH EXCLUSIVE` precludes one — strongly
suggests a deeper coherency issue or the chain reflects an
intermediate state that no single fiber actually reached.

**Remaining work:** Likely needs a packed atomic state per Task
(combine `waiting_for_lock` + `waiting_for_lock_owner` into a single
`u128` so a single atomic load gets a coherent snapshot), or a per-
Task sequence counter for retry-loop validation. Both require touching
`queues.zig` and the parking-lot park/unlock/wake paths in tandem.

**Existing parking-lot tests** (`zig/parking-lot-test.zig`'s 31
tests) still pass — the partial fix is a strict improvement; only
the bench at THREADS≥4 still panics.

**Repro:** `./clear build benchmarks/concurrent/14_nested_lock/bench.clear -o /tmp/b && CLEAR_THREADS=4 /tmp/b`
