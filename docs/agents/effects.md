# Effects System

CLEAR's effects system is a compile-time mechanism that tracks what side-effects a function can produce. It enables three things:

1. **STRICT mode** — public APIs must declare their effects; the compiler verifies them.
2. **#HOT annotations** — mark performance-critical functions; the compiler proves they are deterministic.
3. **Profile-Guided Optimization** — the compiler uses effect data to make better optimization decisions automatically.

The effects system is **not** function coloring. Effects are only required on public library boundaries (and can be auto-generated by the compiler). End-users writing application code never need to think about effects unless they opt into STRICT mode.

## The Effects

| Effect | Meaning | Source |
|---|---|---|
| `HEAP` | Dynamic allocation (GPA, arena escape) | `@list`, `HashMap`, capability wraps (`@shared`, `@locked`, `@boxed`) |
| `BLOCKING` | May yield the fiber waiting for a lock | `WITH EXCLUSIVE` or auto-lock field mutations on `@locked`/`@writeLocked` |
| `REENTRANT` | Function is directly or indirectly recursive | `EFFECTS REENTRANT` declaration, mutual recursion cycles |
| `LOOP_UNBOUND` | Contains a loop without a provable bound | `WHILE TRUE`, `BG STREAM` generators |
| `EXTERN` | Calls native code (opaque to the compiler) | `EXTERN FN` calls |
| `FILE_READ` | Reads from the filesystem | Future: annotated `EXTERN FN` |
| `FILE_WRITE` | Writes to the filesystem | Future: annotated `EXTERN FN` |
| `NETWORK_READ` | Reads from a network socket | Future: annotated `EXTERN FN` |
| `NETWORK_WRITE` | Writes to a network socket | Future: annotated `EXTERN FN` |

`HEAP`, `BLOCKING`, `REENTRANT`, `LOOP_UNBOUND`, and `EXTERN` are tracked silently today. The FILE/NETWORK effects will be added when `EXTERN FN` declarations gain effect annotations.

## How It Works

### Silent Tracking (v0.1)

The compiler already tracks effects for every function — you just can't see them yet. During semantic analysis:

1. **Direct collection**: Each `visit_*` method records effects as it encounters them (e.g., `visit_HashLit` records `HEAP`, `visit_WithBlock` records `BLOCKING` for `EXCLUSIVE` access).
2. **Transitive propagation**: After all functions are analyzed, a fixed-point pass propagates effects through the call graph. If `foo()` calls `bar()`, and `bar` has `HEAP`, then `foo` inherits `HEAP`.
3. **Storage**: The computed effect set is stored on each `FunctionDef` AST node as a frozen Set.

This means the infrastructure is already in place. STRICT mode and `#HOT` just add enforcement on top.

### STRICT Mode (v0.2+)

```
-- ILLUSTRATIVE
-- Compile with: clear build --strict
FN handle_request(req: Request) RETURNS Response
  EFFECTS HEAP, NETWORK_READ
  RETURNS Response ->
  ...
END
```

In STRICT mode:

- **Public functions** (`PUB FN`) must declare their effects with an `EFFECTS` clause.
- The compiler verifies the declaration matches the computed effects. Missing an effect is a compile error. Declaring an effect you don't use is a warning.
- **Private functions** don't need declarations — the compiler infers them.
- **The compiler can auto-generate declarations**: `clear fix --effects` analyzes your code and inserts the correct `EFFECTS` clauses for all public functions.

This is not function coloring because:
- Only public boundaries need annotations (not every function in the call chain).
- The compiler can write the annotations for you.
- Application code (non-library) never needs them unless you opt into STRICT.

### #HOT Annotation (v0.2+)

```
-- ILLUSTRATIVE
#HOT
FN tick(entities: Entity[10000]@pool:soa) RETURNS Void ->
    entities s> EACH { _.x = _.x + _.vx; _.y = _.y + _.vy; };
    RETURN;
END
```

`#HOT` tells the compiler: "This function must be deterministic. No allocation, no blocking, no syscalls." Specifically, `#HOT` rejects:

| Rejected Effect | Why |
|---|---|
| `HEAP` | Allocation can trigger a page fault (~3000ns), destroying predictable latency |
| `BLOCKING` | Mutex acquisition can yield the fiber, adding unbounded latency |
| `EXTERN` | Native calls are opaque — the compiler can't prove they don't allocate or block |
| `NETWORK_READ/WRITE` | Syscalls enter the kernel (~1000ns minimum) |
| `FILE_READ/WRITE` | Disk I/O is orders of magnitude slower than compute |

`#HOT` **allows**:
- `REENTRANT` — recursion is deterministic if stack-bounded (enforced by the control plane's OnOverflow)
- `LOOP_UNBOUND` — game loops and tick functions are inherently unbounded

**Note on Tail Call Optimization (TCO):** Currently, tail-recursive functions still require the `REENTRANT` effect because the compiler does not yet detect or transform tail calls. In v0.2, the compiler will identify tail-recursive patterns and either transform them into loops (eliminating `REENTRANT`) or emit Zig's `@call(.always_tail, ...)` for guaranteed TCO. Until then, tail-recursive functions are treated identically to general recursion.

When a `#HOT` function transitively calls something with a rejected effect, the compiler emits:

```
Error: #HOT function 'tick' transitively calls 'processItem' which has effect HEAP.
       processItem (line 42) → allocates via List[] (line 45)

       To fix: pre-allocate outside the hot loop, or use a stack-allocated fixed array.
```

The error includes the full effect chain so you know exactly where the violation originates and how to fix it.

### The Workflow: Normal Code to HFT-Standard

The power of this system is the upgrade path. You write normal, readable code:

```
-- ILLUSTRATIVE
FN process_orders(orders: Order[10000]@pool) RETURNS Void ->
    orders s> EACH { handle_order(_); };
    RETURN;
END
```

When you need performance, add `#HOT`:

```
-- ILLUSTRATIVE
#HOT
FN process_orders(orders: Order[10000]@pool) RETURNS Void ->
    orders s> EACH { handle_order(_); };
    RETURN;
END
```

The compiler immediately tells you what's wrong:

```
Error: #HOT function 'process_orders' transitively calls 'handle_order' which has effect HEAP.
       handle_order (line 15) → List[] constructor (line 18)
```

You fix `handle_order` to pre-allocate or use a fixed array. Repeat until the compiler is satisfied. Now your hot path is **provably** allocation-free, blocking-free, and syscall-free — the same guarantees an HFT engineer would verify by hand, but enforced by the compiler.

## Profile-Guided Optimization

The effect system enables the compiler to make optimization decisions that are normally reserved for profile-guided optimization (PGO), but **at compile time** without profiling runs.

### Stack Size Selection

The control plane already uses runtime heuristics (OnOverflow/OnUnderflow) to pick fiber stack sizes. With effects, the compiler can make better initial guesses:

| Effect Profile | Recommended Stack | Rationale |
|---|---|---|
| No effects | MICRO (4 KB) | Pure compute, minimal stack usage |
| HEAP only | STANDARD (16 KB) | Allocator may use some stack for bookkeeping |
| REENTRANT | LARGE (64 KB) | Recursive call chains consume stack linearly |
| REENTRANT + HEAP | XL (256 KB) | Worst case: deep recursion with per-frame allocations |

### Scheduler Hints

- **BLOCKING functions** → the scheduler can pre-emptively move other work off the thread, avoiding head-of-line blocking when a fiber enters `WITH EXCLUSIVE`.
- **Effect-free functions** → candidates for inlining and loop vectorization (no side-effects to preserve ordering for).
- **LOOP_UNBOUND** → the scheduler inserts yield points (`checkYield()`) to prevent fiber starvation.

### Arena Mode Selection

- Functions with `HEAP` but no `BLOCKING` → candidates for `@arena` mode (bulk-free on fiber exit instead of per-function rewind).
- Functions with neither `HEAP` nor `BLOCKING` → frame arena isn't needed; the compiler can skip `saveFrameMark`/`restoreFrameMark` entirely.

## Security Sandboxing (Future)

Effects enable **capability-based security** at the package level:

```
-- ILLUSTRATIVE
-- In build.zig.zon or package manifest:
-- package "json-parser" allows: [HEAP]
-- package "http-client" allows: [HEAP, NETWORK_READ, NETWORK_WRITE]
-- package "logger" allows: [HEAP, FILE_WRITE]
```

A JSON parser that declares `EFFECTS HEAP` but transitively calls `NETWORK_WRITE` is a compile-time rejection. This catches supply-chain attacks where a dependency does something it shouldn't — without sandbox overhead at runtime.

## Design Principles

### Effects Are Not Function Coloring

In languages with explicit effect systems (Koka, Haskell), every function in the call chain must declare its effects. This creates "function coloring" — adding an effect to a leaf function forces changes to every caller up the chain.

CLEAR avoids this because:

1. **Effects are inferred**, not declared. The compiler computes them from the implementation.
2. **Declarations are only required at public API boundaries** (STRICT mode) or performance-critical paths (`#HOT`).
3. **The compiler can auto-generate declarations** (`clear fix --effects`), so even the boundary annotations are low-friction.

### Effects Are Verified Documentation

Think of effect declarations as doc comments that the compiler checks. They tell the reader "this function allocates" or "this function may block" — and the compiler ensures the documentation doesn't lie.

### Effects Don't Change Semantics

Effects never change what your code does. They are purely a **verification layer**:
- Without STRICT mode: effects are tracked silently, used internally for optimization hints.
- With STRICT mode: effects are verified against declarations, catching architectural violations at compile time.
- With `#HOT`: effects are used to prove determinism, catching performance violations at compile time.

Your code runs identically regardless of whether effects are declared.

## Relationship to Other Features

| Feature | Relationship to Effects |
|---|---|
| **Capabilities** (`@shared`, `@locked`) | Capabilities are the *source* of HEAP and BLOCKING effects |
| **Control Plane** (OnOverflow/OnSkew) | Effects inform initial stack size and scheduling decisions |
| **SOA** (`@pool:soa`) | Effect-free pipelines are candidates for SIMD vectorization |
| **CONCURRENT** | Worker pools inherit effects from the pipeline body |
| **@arena / @pinned** | Effect analysis determines which fibers benefit from arena mode |
