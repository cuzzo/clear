# Ruby-to-CLEAR Migration Feature Gaps

## Lexer Migration

- `String@symbol` is expected to work as a first-class token/tag representation. CLEAR should accept symbol literal expressions like `.NAME`/`:NAME` as string values typed `String@symbol`; this is not intended to be an unsupported expression form. The migration exposed bugs rather than a missing language feature: ruby-to-clear initially emitted `.NAME` in places the compiler could not parse, the parser originally rejected uppercase symbol literals such as `:ELLIPSIS`, and symbol equality is currently pointer-based enough that equivalent literals from imported modules can compare unequal. Lexer tests compare tag text as a workaround, and the lexer avoids `token.type == :EOF` for the same reason.
- Regex and scanner support remain the largest migration gap. The Ruby lexer is built around `StringScanner#scan`, regex captures, interpolated regexes, and Ruby match operators. ruby-to-clear currently has to emit `unsupportedRuby(...)` placeholders for most of that surface.
- String interpolation has no obvious literal escape for the two-character sequence `"${"`. The migrated lexer source had to avoid writing that string directly and instead compare `"$"` and `"{"` separately.
- The lexer migration exposed missing byte/codepoint conversion helpers. Ruby can do `hex.to_i(16).chr(Encoding::UTF_8)`; CLEAR currently needs hand-written ASCII-only conversion for `\xHH`/`\u{...}` escapes.
- Raw string single-byte access is awkward. The migrated lexer uses one-character `substr` slices plus `"" +` coercions because raw string byte access returns `String@raw`, while most helper predicates need ordinary `String`.
- Function calls over mutable scanner state in `WHILE` conditions can be hoisted incorrectly. `WHILE self.pos < len && is_identifier_body?(current_char(self))` generated Zig that reused the first `current_char` result for the whole loop. The lexer now computes those predicates inside loop bodies.
- Checked numeric casts are missing or poorly lowered. After an explicit `UInt64` range check, `CAST(value AS Int64)` still lowered to an invalid Zig `@as(i64, value)`. The lexer currently converts through `value.toString().toInt()` as a safe but inefficient workaround.
- `ASSERT_RAISES` lowering failed for fallible expressions returning list and scalar payloads during the lexer tests. The migrated tests use explicit `CATCH` helpers for overflow rejection instead.
- Local build/test caching did not reliably invalidate when only a required CLEAR file changed. During migration, generated test binaries had to be removed manually after edits to `compiler/src/ast/lexer.clear`.
- Top-level immutable lookup tables would help migrations. The lexer keyword set and numeric suffix ranges became long predicates because ruby-to-clear cannot preserve Ruby constants such as `KEYWORDS = ...to_set` in a useful CLEAR shape yet.
- RSpec specs do not translate meaningfully yet. ruby-to-clear now keeps unsupported RSpec/block DSL output syntax-valid as `unsupportedRuby(...)` placeholders in lax mode, but the real tests still have to be rewritten manually into CLEAR `TEST` blocks.

## Parser Migration

- CLEAR does not currently parse array/hash literals as parameter defaults, for example `FN f(xs = []: String[])`. ruby-to-clear now omits those defaults rather than emitting invalid syntax, but this loses Ruby default-argument behavior and must be filled in manually where the default matters.
- Unknown Sorbet collection types such as bare `T::Array`, `T::Hash`, and `T::Set`, or collections whose element type resolves to `Auto`, cannot be emitted as `Auto[]`/`HashMap<Auto, Auto>` because those are invalid CLEAR type syntax. ruby-to-clear currently collapses them to `Any`; a richer migration needs explicit generic placeholders or concrete local types.
- CLEAR rejects wrapped `Auto` forms such as `?Auto` and `!Auto`; ruby-to-clear now emits plain `Auto` when a nullable or fallible type cannot be made concrete. This keeps translated code parseable but hides optional/error-union intent until the migration has explicit types.
- CLEAR collection type syntax does not currently accept annotated element forms such as `String@symbol[]@set`. ruby-to-clear strips element annotations in collection types, for example `T::Set[Symbol]` becomes `String[]@set`, which is parseable but loses symbol-string specificity.
- CLEAR symbol literals still collide with keywords. Ordinary Ruby symbols can emit as `:name`, and non-keyword uppercase names such as `:ELLIPSIS` parse, but keyword symbols such as `:VIEW` and `:SNAPSHOT` must currently be emitted as `symbol("VIEW")`/`symbol("SNAPSHOT")`. This keeps parser output syntax-valid, but a first-class `String@symbol` literal form should not require call syntax for keyword names.
- `COMPTIME IF T IS_A String@symbol THEN` now parses and lowers, but `@symbol` is still an erased string capability in Zig type equality. The emitted predicate compares `T` to `[]const u8`, so it supports the source form but cannot distinguish plain `String` from `String@symbol` until CLEAR has capability-aware generic type metadata or non-erased type values.
- Parser translation depends on Ruby metadata from required files. ruby-to-clear now recursively preloads `Struct.new`/`T::Struct` field names and class `initialize` parameters through guarded and unguarded `require_relative` calls, which removes parser-source and parser-test constructor placeholders.
- The generated parser and parser-focused tests currently contain zero `unsupportedRuby(...)` markers. Remaining semantic gaps are explicit helper calls such as `regexMatch?`, `regexReplaceFirst`, `regexReplaceAll`, `regexCapture`, `isA?`, `respondsTo?`, and `eachWithIndex()`. CLEAR needs real stdlib/runtime definitions or manual rewrites for these helper surfaces before the generated parser can compile and run.
- Fixed during this migration: the Ruby parser's pattern engine no longer uses `send("parse_#{item}")`, and pattern constructors no longer use dynamic `node_class.new(start_token, *args)`. The Ruby source now has explicit pattern-action branches and explicit pattern constructor blocks, so generated parser output does not depend on `dynamicSend(...)` or `splat(...)`.
- Fixed during this migration: ruby-to-clear now lowers static `send(:method, ...)` calls to direct method calls and rejects dynamic send targets or Ruby splat arguments instead of emitting runtime helper surfaces such as `dynamicSend(...)`/`splat(...)`.
- Keyword calls cannot be emitted directly because CLEAR has no Ruby-style keyword-call syntax. ruby-to-clear now maps known method/constructor keyword calls to positional arguments and lowers unknown keyword calls to a final hash argument. Helper APIs such as `error!`/`fixable!` will need CLEAR signatures that explicitly accept those option maps.
- The Ruby parser's dynamic rule tables (`@@stmt_rules`, `@@primary_rules`, `@@suffix_rules`) now translate to shared lower-case CLEAR variables, and block registrations translate to lambda values. The remaining issue is semantic: the generated dynamic parser table approach still needs concrete CLEAR-compatible callback/table definitions.
- Ruby `loop do ... end` and assignment-heavy `while (x = ...) && ...` predicates now lower to `WHILE TRUE` loops with explicit assignment guards. This is parseable and closer to Ruby semantics, but still deserves review in migrated control-flow hot paths.
- Ruby regex literals, match operators, `$1`, and regex-backed `gsub/sub` now lower to explicit regex helper calls. This removes placeholder blobs, but CLEAR still needs first-class regex/capture APIs for executable migrated code.
- Iterator blocks with multiple parameters now lower through tuple indexing (`_[0]`, `_[1]`) and simple destructured lambda parameters lower through setup locals. This handles the parser migration cases, but richer Ruby enumerable destructuring still needs either CLEAR language support or manual loops.
- Ruby heredocs now lower to CLEAR triple-quoted strings (`"""..."""`) instead of raw newlines inside ordinary quoted strings. This is the right target syntax for parser specs that use `<<~CLEAR`, but delimiter-containing content still falls back to escaped single-line strings.
- Ruby mixins and helper dependencies are not migrated. Calls such as `include ErrorHelper` parse if emitted as normal calls, but fail compile-time name resolution; the parser needs CLEAR equivalents for AST, type, error, and fixable-helper APIs before generated parser code can compile.
- Parser RSpec files now translate into real CLEAR `TEST`/`WHEN`/`TEST THAT` blocks for simple `expect(...).to eq/be/be_a/all(be_a)/be_nil/be_truthy/be_falsey/include` and `raise_error` forms. They are no longer placeholder stubs, but they still depend on the migrated parser, lexer, AST/types, and helper runtime being available.
