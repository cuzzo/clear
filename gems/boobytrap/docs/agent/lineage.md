# Deep Lineage Engine: High-Fidelity Historical Risk

This document outlines the design for the `Lineage` engine: a standalone Rust-based tool that tracks logical code units (functions/classes) across file renames, moves, and refactors. It serves as the industrial-grade history provider for the `Boobytrap` gem.

## 1. The Core Problem: Rename Blindness

Current historical risk tools (including the standard Boobytrap "Bugspots" implementation) are **file-granular**. If a high-risk function in `socket.rb` is moved to `transport.rb` during a refactor, its history is reset to zero. The "Bugspot" score disappears, and the system loses its memory of that logical unit’s fragility.

## 2. Technical Specification: The `Lineage` Engine

The `Lineage` engine is a concurrent log parser written in Rust, leveraging `tree-sitter` for boundary detection and a pluggable VCS adapter model.

### A. Functional Tracking
- **Mechanism:** Instead of tracking file paths, the engine tracks **Logical IDs**. A Logical ID is generated by combining the AST signature of a function (via Tree-sitter) and its relative position in the file.
- **Mapping:** It performs a concurrent walk of the commit graph. For every hunk in a diff, it identifies which AST node the change belongs to. If a hunk represents a move (deleted in A, added in B), the Logical ID is preserved.
- **Change Discrimination:** The engine must distinguish between "Logical Mutations" and "Aesthetic Changes" to prevent score inflation:
  - **Pure Moves:** Moving a function or block within a file or between files with zero logical delta (verified via normalized AST) is flagged as a `MOVE`. It does **not** increment the churn or bugspot score.
  - **Whitespace/Formatting:** Commits that only change indentation, line breaks, or comments are identified via semantic diff and ignored for risk scoring.
  - **Actual Changes:** Only deltas that modify the normalized AST of the logical unit are counted as "Logical Mutations" or "Bugfixes."

### B. VCS Adapter Architecture (Plug-in Model)
While the initial implementation targets **Git**, the engine must use a plug-in architecture to allow for trivial expansion to other version control systems.
- **VcsProvider Trait:** The Rust core defines a trait for repo traversal (`list_commits`, `get_tree`, `diff_blobs`, `get_metadata`).
- **Initial Implementation:** `GitProvider` (leveraging `git2-rs`).
- **Future Targets:** `JujutsuProvider`, `HgProvider`, `SvnProvider`.

### C. Storage: SQLite Database (`lineage.db`)
To support complex architectural queries, Lineage stores its findings in a portable SQLite database.
- **Table: `logical_units`** — id, name, type, original_path, created_at.
- **Table: `events`** — unit_id, commit_hash, event_type (CHANGE|MOVE|FIX), lines_added, lines_removed, timestamp.
- **Table: `metadata`** — commit_hash, message, sentry_id, coverage_delta.

### D. Effort Estimation
- **Scope:** ~1,000 - 1,500 Lines of Code in Rust.
- **Timeline:** ~2 weeks for a solo developer/LLM orchestration.
- **Performance Goal:** Process 10,000 commits in < 10 seconds.

## 3. The Value Proposition for Boobytrap

### A. From File-Level to Logic-Level
Boobytrap moves from saying "This file is hot" to saying "This specific function is a bug magnet." This allows for much more surgical LLM-assisted refactoring.

### B. Time Decay and Value
**Important Note on Decay:** Boobytrap scoring decay is time-weighted (newer fixes matter more). Consequently, if a function fixed 3 years ago is moved today, its lineage score correctly remains low. The value of Lineage is not in "remembering everything forever," but in **preserving the context of the recent high-value window** during major structural reshuffling.

## 4. Cross-Gem Utility

Lineage is a high-signal data provider for the entire suite:
- **Decomplex (Must Build):** To identify "Semantic Clone Risk." If Decomplex finds two identical blocks of code, it can ask Lineage if *either* block has a history of bugfixes. If so, both are flagged as high risk.
- **Nil-kill (Nice to Have):** To verify if a previous nil-fix was attempted on a logical unit and subsequently reverted or broken. It acts as a "Historical Sanity Check" for Z3 inferences.
- **Espalier (Nice to Have):** To generate "Evolutionary Heatmaps," visualizing which parts of the architecture are in a state of constant churn.

## 5. Verdict: Must Build

For a standard Ruby linter, this is overkill. For an **AI-Orchestrated Engineering Suite**, this is a **Must Build**. It provides the "Temporal Depth" that LLMs need to make safe architectural decisions. Without Lineage, the toolchain is "temporally shallow," losing its most valuable lessons every time a developer renames a file.
