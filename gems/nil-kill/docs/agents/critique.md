# Architectural Critique: Nil-kill Alignment with Decomplex & FactMine

This document critiques the sub-optimal design choices in the `nil-kill` codebase, analyzes findings from the Decomplex and Espalier runs, and classifies required architectural refactorings as either planned or additional work.

---

## 1. Sub-optimal Architectural Boundaries & Sloppy Design

Compared to `Decomplex` and `FactMine`, which strictly separate concrete language syntax, AST normalization, stateless fact extraction, and stateful detectors, `nil-kill` suffers from structural coupling:

### A. Custom Syntax Facade Duplication (`nil_kill/syntax.rb`)
- **The Issue**: Instead of consuming language-neutral normalized facts from `FactMine`, Nil-kill maintains its own parser facade and custom Ruby AST subclasses (`CallNode`, `DefNode`, `ClassNode`, etc.) mapping from Tree-sitter.
- **Why It is Sub-optimal**: It duplicates the normalizer and adapter code inside FactMine. It forces Nil-kill's static analysis passes (like `fallibility_pressure.rb` and `hidden_enum_pressure.rb`) to be tightly coupled to Ruby grammar structures. This defeats the "cross-language" design goal.

### B. Web of Messy Dependencies
- **The Issue**: A tightly coupled dependency web exists between the custom syntax AST, static analysis, type inference solving (`infer.rb`), and the Z3 solver (`z3_solver.rb`).
- **Why It is Sub-optimal**: The core engine must walk syntax trees, parse RBI files, compile Z3 equations, and update inference state at the same time. Changing syntax parsing breaks Z3 equations, and changing type representations breaks the report formatting.

## 2. Decomplex Run Findings (Structural Complexity)

Running Decomplex over `gems/nil-kill/lib` revealed severe cognitive complexity and convergence hotspots:

- **`NilKill::Infer#hash_record_expand_row_from_return_origins`** (`lib/nil_kill/infer.rb:397`)
  - *Metrics*: Flagged by **9 independent detectors** (Score: 21). High Decision Pressure, Derived-State Staleness, and State-Based Branch Density.
  - *Root Cause*: Coordinates too many separate concerns (evaluating return origins, resolving struct keys, handling nested types, Z3 solver preparation) inside a single helper.
- **`NilKill::SourceIndex` Reopened Classes** (`lib/nil_kill/source_index/`)
  - *Hotspots*: `expression_type_uncached` and `hash_shape_for_block_return` converge heavily on State-Based Branch Density, Locality Drag, and Missing Abstractions.
  - *Root Cause*: Reopening the class across files hides method/state coupling and leads to large, unreadable files that do ad-hoc syntax pattern-matching.

## 3. Espalier Run Findings (Architecture & Encapsulation)

Running Espalier over `gems/nil-kill/lib` identified massive class-level cohesion and state ownership issues:

- **`NilKill::Report`** (State Owner Score: 366.55, Encapsulation Score: 370.70)
  - *Issues*: 20 state fields, 299 public methods, 0 private methods.
  - *Root Cause*: Acts as a "god class" that manages CLI arguments, HTML/Markdown formatting, and type pressure logic all in one place.
- **`NilKill::SourceIndex`** (State Owner Score: 314.95, Encapsulation Score: 281.90)
  - *Issues*: 15 state fields, 208 public methods.
  - *Root Cause*: Manages type indices, RBI file loading, static/dynamic lookup caches, and local flow graphs.
- **`NilKillRuntimeTrace`** (Cohesion LCOM: 112.6, 8 independent state components)
  - *Issues*: 29 state slots, 8 disconnected state components.
  - *Root Cause*: Blends thread-safe lock management, objects/finalizers, stack frame tracing, and mutation logs.

## 4. Remediation Plan: Planned vs. Additional Work

| Architectural Issue | Identified Hotspots | Remediation Strategy | Plan Status |
|---|---|---|---|
| **Syntax/AST Duplication** | `nil_kill/syntax.rb` | Eliminate `nil_kill/syntax.rb`. Force the static analysis layer to consume normalized facts generated by Decomplex and FactMine. | **Planned** (documented in `multi-language-static-analysis-fix.md`) |
| **RBI & Project Index Coupling** | `infer.rb`, `static_analysis.rb` | Separate Sorbet RBI index compilation and project method return resolution into a dedicated language-specific provider backend. | **Planned** (documented in `multi-lang-support.md`) |
| **Inference Phase Boundaries** | `infer.rb` | Restructure Nil-kill's execution into five clean sequential phases: (1) Ingestion & Normalization, (2) Flow Propagation & Constraint Solving, (3) Stateful Pressure Scanning (independent of parsing), (4) Action Generation, and (5) Output Rendering. | **Implemented** |
| **God Class: `NilKill::Report`** | `report.rb` | Extract phase-state records, separate metric calculators from Markdown/HTML formatting utilities. | **Additional Work** (needs new issue) |
| **God Class: `NilKill::SourceIndex`** | `source_index/` | Extract separate coordinator classes, and split local flow/resolver caches from static facts. | **Additional Work** (needs new issue) |
| **Low Cohesion: `NilKillRuntimeTrace`** | `runtime_trace.rb` | Split the runtime tracer into a lightweight writer, an independent stack-frame tracking helper, and a separate finalizer controller. | **Additional Work** (needs new issue) |

## 5. Ruby-Specific Details to Extract to Fact-Mine & SCM Query Files

To make Nil-kill truly language-agnostic, the following Ruby-specific syntactic matching patterns must be extracted into language-specific `.scm` Tree-sitter query files or compiled Fact-Mine rules:

### A. Fallibility / Exception Roots
- **Current Ruby Coupling**: Hardcoded symbols `raise`, `fail`, `error!` inside `FallibilityPressure`.
- **Extraction Target**: Define SCM query files (e.g. `queries/<language>/fallibility.scm`) to capture raise/throw/panic statements and exception instantiation calls:
  - Ruby: `(raise_statement) @fallibility.raise`
  - Python: `(raise_statement) @fallibility.raise`
  - JS/TS: `(throw_statement) @fallibility.throw`
  - Rust: `(macro_invocation macro: (identifier) @m_name (#eq? @m_name "panic")) @fallibility.panic`

### B. Exception Handlers (Rescue/Except/Catch Blocks)
- **Current Ruby Coupling**: Hardcoded checks for `Syntax::RescueNode`, `Syntax::RescueModifierNode`, and `Syntax::BeginNode`.
- **Extraction Target**: Define SCM query files to capture rescue/except/catch structures:
  - Ruby: `(rescue_modifier) @handler.rescue` and `(rescue) @handler.rescue`
  - Python: `(except_clause) @handler.rescue`
  - JS/TS: `(catch_clause) @handler.rescue`

### C. Literal Collections & Schema Extraction
- **Current Ruby Coupling**: Matches Ruby `HashNode` and `ArrayNode` literals directly inside AST traversers to extract shapes.
- **Extraction Target**: Abstract collection extraction into `Decomplex::Adapter` or `.scm` files to generate normalized map/tuple facts:
  - Ruby: `(hash) @literal.map` and `(array) @literal.tuple`
  - Python: `(dictionary) @literal.map` and `(list) @literal.tuple`

### D. Mixin / Hierarchy Propagation
- **Current Ruby Coupling**: Parses Ruby `include`, `extend`, `prepend` calls directly.
- **Extraction Target**: Move class inheritance, interface implementation, and mixin facts to Fact-Mine's `type_definitions` section, using SCM definitions to resolve multi-inheritance and composition.
